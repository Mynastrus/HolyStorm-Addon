# Character Snapshot Pipeline

This document describes the production path in LIVE as of the current main audit. Feature modules own collection and domain validation. PlayerData owns block validation, semantic equality, revisions, timestamps, persistence, and accepted remote imports.

## Shared lifecycle

1. A game event, module bootstrap, CharacterScanManager bootstrap, capability request, or /hs scan command requests a registered block provider.
2. CharacterScanManager deduplicates requests by block, orders them by provider priority, and runs one provider workflow at a time. It loads an unloaded provider through AddonLoader when needed.
3. TaskManager and WorkflowManager run the provider's scan and validation steps. A retry returns to collection and obtains fresh data. Chunked Raid discovery yields through its workflow task.
4. The feature validator rejects missing, incomplete, unavailable, or internally inconsistent data. PlayerData validates again at the owned write and remote import boundary.
5. PlayerData compares the feature payload without root snapshot/core metadata. Equal data returns UNCHANGED; changed valid data is committed and receives its revision and origin timestamps.
6. PlayerData emits the post-commit update events. SyncManager listens to the owned update event and queues publication for the character domain. Remote imports pass block validation and central owner/revision freshness rules.
7. CharacterStore provides stored block queries to Character UI. Rendering and tab refresh do not initiate producer scans.

PlayerData:RegisterBlock is the block descriptor registry. Descriptors identify fields, owner module, schema and snapshot versions, validator, freshness period, persistence and sync policy, capability, provider, and update event. A feature remains responsible for its own Blizzard APIs and domain rules.

## Central contracts

- Block authority: PlayerData is the sole SavedVariables gateway. Feature modules call WriteOwnedBlock; they do not edit HS_Player_DB.
- Snapshot metadata: GetMetadata supplies stable objectId, guid, block, owner, authoritative revision, origin and commit timestamps, plus the block's schema and snapshot versions. The stored feature payload stays in its existing schema.
- Semantic equality: FingerprintSnapshot omits core/version/timestamp envelope keys at the snapshot root. Multi-field blocks compare each registered field as a snapshot root. Nested feature values remain significant. This avoids timestamp-only revisions without hiding domain fields that happen to share names.
- Revision and time: An owned revision increments only after a validated, changed commit. originCreatedAt and committedAt are set at that origin commit. Remote receive time is separate.
- Last valid: Validation precedes persistence and Sync. Rejected, incomplete, unavailable and timed-out scans do not write; retries recollect. Existing committed data remains queryable.
- Results: Snapshot workflows use VALID, COMMITTED, UNCHANGED, bounded RETRY, and task/workflow failure. A commit returning UNCHANGED is successful and does not publish. A failed write is not reported as a successful workflow.
- Remote freshness: PlayerData keeps the common rules: lower revision is STALE_REVISION; equal identical is NOOP; equal conflicting is SAME_REVISION_CONFLICT; a higher revision is accepted only when owner authority allows it. Self-owned data stays protected. Feature modules add no freshness rules.
- Unknown values: Unknown is not coerced to zero or empty. Equipment requires every slot to be known (empty is false); Mythic+ accepts confirmed zero rating but rejects missing rating; Stats permits numeric zero and nil unknowns; Raid lifetime reliability remains explicit; Delves distinguishes a confirmed empty activity list from unavailable API data.
- Publish events: Feature update events and HS_PLAYERDATA_OWNED_UPDATED are emitted after a committed PlayerData write. No unchanged write emits another owned update. SyncManager queues block publication from that core event.
- Stored UI: Character UI tabs use CharacterStore queries and stored blocks. Producer availability is not a visibility gate. No full scan is called from render, refresh, tooltip, hover, or tab selection.

## Manual scans and future providers

/hs scan <block> requests the same registered CharacterScanManager provider as automatic triggers. /hs scan all walks the registered data declarations and requests their ordinary providers; it does not write data, revisions, or Sync payloads itself.

To add a character block, register its fields, owner, schema/snapshot versions, validator, freshness, sync/persistence policy, capability, and provider in PlayerData:RegisterBlock. Register a CharacterScanManager provider with its block, capability, addon ID, priority, and request callback. Implement collection and domain validation in the feature, then commit only through WriteOwnedBlock. Use CharacterStore for stored UI reads. Keep unknown Blizzard values unknown, use bounded validation retries, and return after UNCHANGED.

## Offline findings and Retail acceptance

The audit found and corrected these pipeline issues: in-memory SnapshotManager fingerprints could short-circuit a scan without checking persisted data after reload; an Equipment write failure was treated as a successful task; the empty-inventory candidate reset between Equipment's two validation scans; Delves converted unavailable weekly API results into empty/false data; Mythic+ treated a missing overall rating like a confirmed zero; and Stats read its baseline through PlayerData instead of CharacterStore. The central descriptor now declares the five audited feature blocks, and root-only metadata comparison is shared by SnapshotManager, Equipment, and PlayerData.

The available API declarations show C_DelvesUI.GetCurrentDelvesSeasonNumber, C_DelvesUI.GetCompanionInfoForActivePlayer, C_WeeklyRewards.GetActivities(World), C_WeeklyRewards.HasAvailableRewards, and the Delves update events. Live Retail return values and event timing remain unverified without a client. No unsupported Delves fields are inferred.

When Retail is available, run /hs scan equipment, /hs scan mythicplus, /hs scan raid, /hs scan delves, /hs scan stats, and /hs scan all; inspect Character Overview and a stored remote character; reload; sync between two clients; inspect BugSack and Holy Storm logs; verify there are no script timeouts or unnecessary repeated Sync publishes; and verify revisions change only for real payload changes. Raid, Sync/freshness, and Stats v2 Retail acceptance also remain open.
